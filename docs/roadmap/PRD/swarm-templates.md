## 1. TL;DR

```
$ evva swarm init
? What should this team do?
  ▸ code-review     — N reviewers by dimension + verifier + leader
    feature-team    — planner/implementer/tester on a task graph
    research        — parallel researchers + synthesizer
    ops-monitor     — watcher members + escalation rules
    docs-crew       — docs writer + fact-checker vs source
    custom          — bare skeleton, all fields prompted
? Repo to work on: ~/work/api
? Reviewers (2-4): 3
✓ wrote .evva/swarm/code-review/   (manifest + 5 member prompts + README)
  review it, then:  evva swarm up code-review
```

A **template** = a parameterized team: manifest skeleton, per-member
prompt files with substitution slots, a task-graph seed (DWF), verify
policies, and a README explaining the team's theory of operation.
`swarm init` is an interview that instantiates one into `.evva/swarm/`
for review — **generated artifacts are plain files the operator owns;**
there is no runtime template magic, no hidden layer. Editing the
output IS the customization story.

Templates live three places, in precedence order: built-in (shipped,
curated, tested), `<EVVA_HOME>/templates/swarm/` (operator-authored),
and — once W18 lands — persona packs may carry team templates (a pack
that ships `nono` can ship a "family-finance team" that uses her).

## 2. Goals / non-goals

### Goals

- Template format: a directory with `template.yml` (params: name,
  type, prompt, default, validation), manifest + prompt files with
  `${param}` slots, optional task-graph seed, README. Deliberately
  the same mental model as the pack format (W18) — one authoring
  skill.
- `evva swarm init [template]`: interview (or `--param k=v`
  non-interactive), instantiation, post-generate summary with next
  steps; refuses to overwrite without `--force`.
- Five shipped templates (the list above), each: reviewed prompts
  (the real craft — these encode swarm best practices: brief-writing,
  verify policies, fan-out sizing from the DWF protocol), sized
  defaults, a smoke-test under `examples/` CI (fake LLM, graph
  executes).
- Template validation: `evva swarm lint <dir>` checks instantiated
  output (manifest schema, prompt slots resolved, graph acyclic) —
  shared with the manifest loader's existing validation.
- Authoring guide: how to turn a working team into a template
  (`swarm templatize <space>` — export a running space's manifest +
  prompts with values lifted to params — is the stretch item, TPL-6).

### Non-goals (this wave)

- A template *registry* beyond the three-tier lookup (pack-carried
  templates arrive with W18; no separate distribution channel).
- Runtime template inheritance/composition (copy-and-edit is the
  model; composition is complexity without demonstrated need).
- Auto-tuning member counts to repo size (defaults + interview; the
  operator knows their repo).
- Templating solo-agent artifacts (personas have packs; workflows
  have examples — this wave is swarm-shaped).

## 3. Design sketch

- **Content is the product:** the engine (params + substitution +
  file copy) is a weekend; the five templates' prompts are the wave.
  Each template gets design review against the current team protocol
  and the swarm PRDs' lessons (verify-checks, blackboard usage,
  cost-accounting awareness) — templates are how those lessons reach
  users who read none of those documents.
- **Interview ergonomics:** param types (string/int/enum/repo-path)
  drive prompts; defaults everywhere; `--yes` accepts all defaults.
  The interview is also the docs — each param's `prompt` text
  teaches what the knob does.
- **Instantiation honesty:** generated files carry a header comment
  (`generated by swarm init from <template>@<version>; edit freely`)
  — provenance without lock-in.
- **CI truth:** every shipped template's smoke test actually runs the
  graph (fake LLM) in CI — templates that rot get caught by the
  build, not by a user's failed demo.

## 4. Work items

- **TPL-1 — Format + engine.** `template.yml` schema, substitution,
  three-tier lookup, `--param`/`--yes`. *Accept:* fixture template
  instantiates correctly; unresolved slots fail lint; precedence
  table-tested.
- **TPL-2 — Interview UX.** Type-driven prompts, validation,
  post-generate summary. *Accept:* scripted interview produces
  byte-expected output; invalid input re-prompts.
- **TPL-3 — Lint.** Shared validation with the manifest loader +
  template-specific checks. *Accept:* seeded defects (cycle, missing
  slot, bad member ref) each produce a distinct, located error.
- **TPL-4 — The five templates.** Content + design review + sized
  defaults. *Accept:* prompt review sign-off; each instantiates
  clean under lint.
- **TPL-5 — CI smoke tests.** Fake-LLM graph execution per template
  under `examples/` CI. *Accept:* all five execute their seed graphs
  green in CI.
- **TPL-6 — `swarm templatize` (stretch).** Export a live space as a
  template skeleton with lifted params. *Accept:* round-trip — 
  templatize a fixture space, re-init it, graphs match.
- **TPL-7 — Docs + changelog.** User-guide (en + zh-tw): using
  templates, the authoring guide, template-vs-pack relationship.

## 5. Risks

| Risk | Mitigation |
|---|---|
| Templates encode today's best practices, then rot | CI smoke tests + templates version with the repo (built-ins update with releases); the generated-file header names the source version |
| Users treat generated teams as black boxes | README per template explains the theory; the interview teaches; files are plain and commented |
| Five templates is the wrong five | they're seeds, not a catalog — the format + authoring guide matter more; usage feedback reorders the investment |
| Overlap confusion with workflow scripts (W16) | the docs draw the line the same way long-range does: workflows are ephemeral step graphs, teams are durable rosters — templates make *teams* |
